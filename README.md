# Shipyard

A **deployment control plane**: Next.js UI → Go control plane → Bash executor →
Linux hosts (git, systemd, nginx, journald).

> **Shipyard is a write-ahead intent ledger plus a single serial Bash executor.**
> Postgres records what we *meant* to do. The target host's filesystem and
> systemd record what is *actually true*. Reconciliation is the self-healing gap
> between them. The UI, API, and state machine are read models over that gap.

**All code here is written by hand, by one person, guided step by step.** The
design work is finished and written down; the implementation is not. There is no
`db/`, no `internal/`, no `cmd/` yet — and that is deliberate. What does exist is
the lab: real hosts, brought up by one command, that everything downstream is
built against.

## The build order

Phase 0 is done. The next one is the ledger — the write-ahead intent record that
everything else is a view over. Read
[`docs/ROADMAP.md`](docs/ROADMAP.md) for the ordered steps and the acceptance
check on each; it is deliberately the only phase list in the repo.

If you only ever do one phase, do the manual `deploy.sh`: clone → build → swap →
restart → health → rollback. It is the product. Everything after it is a control
panel and a ledger over a deploy that actually works.

## The three status axes (the crux)

Orthogonal, and the single most common source of bugs. Do not merge them:

| Axis | Question | Source of truth |
|---|---|---|
| `state` + `state_seq` | What are we *trying* to do? | Postgres (intent) |
| `slot_busy` (derived) | Is a worker on it *right now*? | Generated column — never drifts |
| `is_active` + `active_verified_at` | Is it *live on the host*? | The target host (reality) |

## The lab

The lab is three Ubuntu containers (`shipyard-01/02/03`) that stand in for VPS
targets. Each runs real systemd as PID 1, its own `sshd` on 2201/2202/2203, and
its own nginx on 8081/8082/8083. The engine reaches them over real SSH and knows
nothing about Docker, so the same code path serves a VPS unchanged in Phase 6.

```bash
make lab-up             # build, start, capture host keys, then verify
make lab-check          # assert the fleet is a usable deployment target
make lab-down           # stop, keep keys and host identities
make lab-reset          # stop and discard volumes (rotates every host key)
make lab-rotate-key     # revoke the login keypair
```

`make lab-up` ends with `Lab read.` That line is the Phase 0 acceptance test, and
it is not a formality — every assertion is made *through* a real SSH session as
`deploy` with `StrictHostKeyChecking=yes`, so a pass proves authentication, host
identity and reachability together:

```text
deployment targets
  ok    shipyard-01 reachable at 127.0.0.1:2201 as deploy
  ok    127.0.0.1:2201 is shipyard-01
  ok    shipyard-02 reachable at 127.0.0.1:2202 as deploy
  ...
  ok    systemd is running, readable unprivileged over SSH
  ok    nginx is active
  ok    GET /health returns ok
  ok    /var/www is writable by deploy

Lab read.
```

Each host has its own SSH host key, generated on first boot and kept on a named
volume, so `known_hosts` actually distinguishes the three and strict host key
verification means something. `known_hosts` is keyed by the literal address the
engine dials (`[127.0.0.1]:2201`), because OpenSSH matches host keys on the
string it is handed. Ports are published on loopback only.

The login keypair lives in `infra/lab/keys/` and is generated by a one-shot init
container, never baked into an image — rotate or revoke it without rebuilding
anything.
